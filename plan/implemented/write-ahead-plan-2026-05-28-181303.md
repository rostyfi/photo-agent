# Write-Ahead Log (WAL) Implementation Plan

## 1. Overview & Goals

Add a write-ahead log to every microbatch so processing state survives crashes, power loss, or process restarts. The WAL records each image's processing lifecycle atomically, enabling automatic resume without re-processing completed images.

### Goals

| # | Goal |
|---|------|
| 1 | Atomic, append-only log of every image's processing lifecycle |
| 2 | Crash-safe: never lose completed work; never produce partial/corrupt entries |
| 3 | Automatic resume on restart for both CLI and Web UI paths |
| 4 | Replace O(n) sidecar scanning in `_load_processed_set()` with O(1) WAL lookup |
| 5 | Backward-compatible: existing sidecar JSONs remain the source of truth for per-image results |
| 6 | Unified batch tracking across CLI and Web UI (single WAL per folder) |
| 7 | Detect and recover abandoned "in_progress" entries via timeout |
| 8 | Future-ready: serialize/deserialize through a pluggable codec so the on-disk format can be swapped without touching WAL logic |

### Non-goals

- This is NOT replacing sidecar JSONs. Sidecars remain the per-image result store.
- This is NOT adding persistent distributed coordination (single-process only).
- This is NOT adding real-time streaming/eventing — the WAL is a recovery log.

## 2. WAL File Format

**Location:** `<folder>/.open-photo-agent/wal.jsonl`

**Format:** JSON Lines (one JSON object per line). This is append-only and line-delimited, making it trivially recoverable — if the last line is incomplete (crash mid-write), it is simply discarded on read.

### Entry Schema

```jsonc
{
  "seq": 1,                          // monotonically increasing sequence number
  "image_path": "/abs/path/img.jpg", // absolute path (primary key for dedup)
  "status": "pending",               // pending | in_progress | completed | failed
  "microbatch_id": "2026-05-16-001", // batch run identifier
  "ts": "2026-05-16T10:30:00.123Z",  // ISO 8601 timestamp of this entry
  "attempt": 1,                      // attempt number (incremented on retry)
  "sidecar_path": "/abs/path/.open-photo-agent/data/img.jpg.json",
  "error_code": null,                // ErrorCode string if failed
  "error_msg": null                  // human-readable error if failed
}
```

### Lifecycle Transitions

```
  (discovered)  -->  pending  -->  in_progress  -->  completed
                           \                       /
                            `---->  failed  <----´
```

Every status change appends a **new line** to the WAL. The final status for a given `image_path` is the last entry with that path.

### Microbatch ID

Format: `YYYY-MM-DD-NNN` where NNN is a 0-padded incrementing counter per day, or alternatively `YYYY-MM-DDTHHMMSS`. This groups entries into a logical batch for statistics/reporting.

## 3. Pluggable Codec Layer (Future-Ready Format Abstraction)

The WAL's on-disk serialization format is abstracted behind a codec interface. This means the log entries are always written and read through a codec, never directly as raw JSON. If the project later needs to migrate to a different format (MessagePack, Protobuf, Avro, SQLite-backed, etc.), only the codec implementation changes — the WAL logic and all callers remain untouched.

### 3.1 Codec Interface

```python
# src/wal_codec.py

from abc import ABC, abstractmethod
from typing import Dict

class WalCodec(ABC):
    """Pluggable serializer/deserializer for WAL entries."""

    @abstractmethod
    def encode(self, entry: Dict) -> bytes:
        """Serialize a WAL entry dict to raw bytes (appended to the log file)."""
        ...

    @abstractmethod
    def decode(self, line: bytes) -> Dict:
        """Deserialize a single raw log line back to a WAL entry dict.

        Raises WalDecodeError if the line is corrupt/truncated.
        """
        ...

    @property
    @abstractmethod
    def file_extension(self) -> str:
        """Return the file suffix for this codec (e.g. '.jsonl', '.msgpack')."""
        ...

    @property
    @abstractmethod
    def name(self) -> str:
        """Human-readable codec identifier (e.g. 'jsonl', 'msgpack')."""
        ...
```

### 3.2 Default Implementation: JSONL Codec

```python
class JsonlCodec(WalCodec):
    """JSON Lines codec — the default and initial format."""

    def encode(self, entry: Dict) -> bytes:
        return (json.dumps(entry, ensure_ascii=False) + "\n").encode("utf-8")

    def decode(self, line: bytes) -> Dict:
        return json.loads(line.decode("utf-8"))

    @property
    def file_extension(self) -> str:
        return ".jsonl"

    @property
    def name(self) -> str:
        return "jsonl"
```

### 3.3 Codec Resolution

The WAL module determines the codec from the log file's extension on disk:

```
wal.jsonl   → JsonlCodec
wal.msgpack → MessagePackCodec (future)
wal.avro    → AvroCodec (future)
```

This is handled in `WriteAheadLog.__init__`:

```python
_CODEC_REGISTRY: Dict[str, Type[WalCodec]] = {
    ".jsonl": JsonlCodec,
    # ".msgpack": MessagePackCodec,  # future
}

@classmethod
def register_codec(cls, extension: str, codec_cls: Type[WalCodec]) -> None:
    cls._CODEC_REGISTRY[extension] = codec_cls
```

### 3.4 Migration Path

When a future format replaces JSONL:

1. Implement a new `WalCodec` subclass
2. Register it via `register_codec(".msgpack", MessagePackCodec)`
3. Write a one-shot migration script that reads the existing `wal.jsonl`, rewrites to `wal.msgpack`, deletes the old file
4. All subsequent runs use the new codec automatically via extension detection

No changes to `WriteAheadLog`, `main.py`, `callbacks.py`, or `discovery.py` are needed.

### 3.5 How the Codec Plugs into WriteAheadLog

```python
class WriteAheadLog:
    def __init__(self, folder: str, codec: Optional[WalCodec] = None) -> None:
        if codec is None:
            codec = self._resolve_codec(folder)  # auto-detect from existing file
        self._codec = codec
        self._path = Path(folder) / ".open-photo-agent" / f"wal{codec.file_extension}"
        ...

    def append(self, ..., entry: Dict) -> int:
        raw = self._codec.encode(entry)
        # ... atomic append raw bytes ...
```

The caller never constructs raw JSON — it passes a dict, and the codec handles the rest.

## 4. New Module: `src/wal.py`

### 4.1 Public API

```python
# src/wal.py

class WriteAheadLog:
    """
    Append-only JSONL write-ahead log for batch processing crash recovery.

    Lives at <folder>/.open-photo-agent/wal.jsonl
    """

    def __init__(self, folder: str) -> None: ...

    def append(self, image_path: str, status: str, microbatch_id: str,
               attempt: int = 1, sidecar_path: Optional[str] = None,
               error_code: Optional[str] = None,
               error_msg: Optional[str] = None) -> int:
        """Atomically append one entry. Returns the sequence number."""
        ...

    def get_status(self, image_path: str) -> Optional[str]:
        """Return the last known status for an image (pending/in_progress/completed/failed)."""
        ...

    def get_pending(self) -> List[str]:
        """Return list of image_paths with last status 'pending' or 'in_progress'."""
        ...

    def get_completed_set(self) -> Set[str]:
        """Return set of image_paths that are completed (for fast dedup)."""
        ...

    def get_failed(self) -> List[dict]:
        """Return list of {image_path, error_code, error_msg} for failed entries."""
        ...

    def get_active_microbatch_id(self) -> Optional[str]:
        """Return the microbatch_id if there are pending/in_progress entries."""
        ...

    def prune(self, keep_completed: bool = True) -> int:
        """Remove stale entries. Returns count removed."""
        ...

    def compact(self) -> int:
        """Compress the WAL: keep only the last entry per image_path.
        Returns the new number of lines."""
        ...
```

### 4.2 Internal Design

- **File locking:** Use `portalocker` (already available, or fall back to `msvcrt.lockf` on Windows / `fcntl.lockf` on Unix) for safe concurrent access between the main process and Dash background callback thread.
- **Atomic append:** Use `open(..., "a")` with `flush()` + `os.fsync()` for performance. The reader is tolerant of a truncated final line.
- **Sequence counter:** Tracked in a companion file `.open-photo-agent/wal.seq` (single integer). Updated atomically via tmp+rename. Alternatively, computed at load time as `max(seq) + 1`.

### 4.3 Read-time Recovery

When `__init__` opens the WAL:
1. Parse all lines via the codec, skipping any unparseable lines (truncated final line).
2. Build an in-memory index: `dict[image_path -> last_entry]`.
3. Identify any entries where `status == "in_progress"` and the timestamp is older than a configurable heartbeat timeout (default: 10 minutes). These are candidates for automatic reset to `"pending"` — an extra entry is appended resetting them.

### 4.4 Compaction

After a batch completes, the WAL may have many lines (3+ per image). A `compact()` method rewrites the WAL keeping only the final entry per `image_path`. This is done atomically (write to temp, rename). Compaction is triggered:
- Automatically when starting a new batch if the WAL exceeds N lines (configurable, default 10,000).
- Manually via `wal.compact()`.

## 5. Integration Points

### 5.1 `src/discovery.py` — `PhotoList.list_photos()` and `_load_processed_set()`

**Before (current):**
```python
# _load_processed_set scans ALL sidecar JSONs in the data/ directory
processed = set()
for f in sidecar_dir.iterdir():
    if f.suffix == ".json":
        data = json.loads(f.read_text(...))
        if data.get("image_path"):
            processed.add(data["image_path"])
```

**After:**
```python
# _load_processed_set uses WAL for O(1) lookup
def _load_processed_set(image_dir: str) -> set:
    wal = WriteAheadLog(image_dir)
    return wal.get_completed_set()
```

**Fallback behavior:** If no WAL file exists yet (legacy folders), fall back to scanning sidecar JSONs and write a WAL entry for each discovered completed image (auto-migration).

### 5.2 `src/callbacks.py` — `queue_all_images()`

**Changes:**
1. At batch start: create `WriteAheadLog(folder)`, generate a `microbatch_id`.
2. For each image path discovered: call `wal.append(path, "pending", microbatch_id)`.
3. Before processing each image: `wal.append(path, "in_progress", microbatch_id)`.
4. After successful processing + sidecar save: `wal.append(path, "completed", microbatch_id, sidecar_path=sidecar_path)`.
5. After failed processing: `wal.append(path, "failed", microbatch_id, error_code=..., error_msg=...)`.
6. Remove `write_batch_state()` calls for progress tracking (the WAL replaces this). Keep `write_batch_state("done", ...)` only for the final completion summary with stats.

### 5.3 `main.py` — CLI path

**Changes:**
1. At batch start: create `WriteAheadLog(containing_folder)`, generate `microbatch_id`.
2. For each discovered image: `wal.append(path, "pending", microbatch_id)`.
3. In the `batch_extract` loop: before extract, `wal.append(path, "in_progress", microbatch_id)`; after extract + sidecar save, `wal.append(path, "completed", microbatch_id, sidecar_path=...)`.
4. Add a `--resume` flag that skips WAL-completed images (read `wal.get_completed_set()`).
5. Add a `--no-resume` flag to force reprocessing all images (still logs to WAL but overwrites previous statuses).

**Note on folder-scoped WAL:** When `main.py` is called with multiple top-level paths (e.g. `main.py folderA folderB file.jpg`), each distinct image parent directory gets its own WAL at `<parent>/.open-photo-agent/wal.jsonl`. The `WriteAheadLog` is instantiated per unique parent directory.

### 5.4 `src/processing.py` — Background thread jobs (future use)

If these legacy thread-based paths are revived, they follow the same WAL protocol. For now, no changes needed — they are dead code.

### 5.5 `src/batch_state.py`

**Keep as-is** for the final batch summary (stats: min/max/avg duration, total time, batch completion timestamp). The WAL tracks per-image status; `batch_state.json` tracks the aggregate summary.

Alternatively, **deprecate `batch_state.json`** and embed the summary as a final special WAL entry:
```json
{"seq": N, "status": "batch_done", "total": 50, "min_duration_ms": 120, ...}
```

**Recommendation:** Keep `batch_state.json` for now to avoid breaking the polling callback. It remains the single source the polling interval reads. The WAL is the recovery mechanism; `batch_state.json` is the UI status display.

## 6. Resume / Recovery Logic

### 6.1 On Application Start (Web UI)

When a user navigates to a folder or clicks "Rescan":
1. Read `WriteAheadLog(folder)`.
2. If `wal.get_pending()` returns entries with status `"in_progress"` and their timestamps are older than the heartbeat timeout:
   - Append new entries resetting them to `"pending"` with `attempt += 1`.
   - Log a warning: "Found N abandoned in_progress entries, resetting to pending."
3. `PhotoList.list_photos(exclude_processed_from)` uses `wal.get_completed_set()` — only truly completed images are excluded.

### 6.2 On Batch Start

1. Generate new `microbatch_id`.
2. Discover images via `PhotoList` (which now excludes WAL-completed images).
3. Append `"pending"` entries for all discovered images.
4. Begin processing loop — each image transitions pending → in_progress → completed/failed.

### 6.3 Mid-batch Crash Scenario

| Step | What's on disk | Recovery action |
|------|---------------|-----------------|
| Crash before `in_progress` written | WAL has `pending` entry for image | Resume: image remains pending, gets picked up in next run |
| Crash during `extract()` | WAL has `in_progress` entry | Heartbeat timeout → reset to pending → retry |
| Crash after sidecar saved but before `completed` WAL entry | Sidecar JSON exists; WAL has `in_progress` | Heartbeat timeout → reset to pending → **sidecar dedup prevents re-processing** (PhotoList checks sidecar existence as fallback) |
| Crash after `completed` WAL entry | WAL + sidecar both present | Image is skipped on resume |

**Defense in depth:** The resume check consults BOTH the WAL completed set AND the sidecar directory. If either indicates completion, the image is skipped. This covers edge cases where the WAL and sidecar are briefly inconsistent.

### 6.4 Heartbeat Timeout

Default: **10 minutes.** Configurable via `OPEN_PHOTO_AGENT_WAL_HEARTBEAT_SECONDS`.

An `in_progress` entry older than this threshold is considered abandoned and reset to `pending`. This accommodates:
- Long model inference times (timeout is 120s per image)
- Brief network glitches that cause retries

## 9. Testing Strategy

### Unit Tests (`tests/test_wal.py`)
- Codec round-trip: encode then decode, verify identical dict
- Append entries and verify sequential ordering
- Verify `get_status()` returns last status for an image
- Verify `get_completed_set()` excludes non-completed images
- Simulate truncated last line — verify reader skips it gracefully
- `compact()`: verify only last entry per image survives
- Heartbeat: write `in_progress` with old timestamp, verify it's listed in pending after init
- Concurrent writers (two threads appending) — verify no interleaved lines

### Integration Tests
- Process a real image → verify WAL has pending, in_progress, completed entries
- Kill process mid-batch → restart → verify resume skips completed images
- Legacy folder with sidecars but no WAL → verify auto-migration seeds WAL

### Manual Verification
- `python main.py ./test-photos --resume` → processes only new images
- Web UI: process folder, stop server, restart, process again → no duplicate processing

## 11. Risk Assessment

| Risk | Likelihood | Mitigation |
|------|-----------|------------|
| WAL grows very large over many batches | Medium | Auto-compaction at threshold; periodic `compact()` call |
| Incomplete last line causes parse error on every read | Low | Reader skips unparseable lines; codec.decode raises `WalDecodeError` which is caught |
| WAL and sidecar get out of sync | Low | Defense-in-depth: both consulted for dedup |
| `in_progress` heartbeat incorrectly resets a slow-but-active job | Low | Heartbeat is 10 min; max timeout is 2 min per image; ample margin |
| Concurrent access from Dash background callback + polling callback | Medium | File lock via `portalocker` or simple `fcntl` / `msvcrt` |
| Future codec migration breaks existing WAL files | Low | Auto-detection via file extension; migration script included; old codec remains available |
